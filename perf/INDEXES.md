# Search indexes: before and after

Migration `a36920872992` (`backend/app/db/migrations/versions/20261115_a36920872992_add_search_indexes.py`).

## Method

- **Data:** 200,000 synthetic issues across 20,000 repos, generated by `perf/bench_queries.py --seed`. The live index has only about 1,200 issues. At that size every query is a sub-millisecond sequential scan, so indexes can't show a difference there. Synthetic data shows how search scales as the index grows.
- **Queries:** the real SQL from `app/api/queries.py` (`issue_search` and `issue_count`), not hand-written copies. One row per kind of request the search page can send.
- **Timing:** Postgres `EXPLAIN ANALYZE` execution time, warm cache, 15 runs per query. Network and API overhead are not included.
- **Machine:** local PostgreSQL 16.15, 16-core laptop. The absolute numbers will differ on Supabase, but the plan changes will be the same.
- **Same data both times:** `--downgrade 0b72fc3abc0f` (before), then `--migrate head` (after).

Reproduce from `backend/` with `scripts/dev-db.sh` running:

```bash
python ../perf/bench_queries.py --seed
python ../perf/bench_queries.py --downgrade 0b72fc3abc0f --label before
python ../perf/bench_queries.py --migrate head --label after
```

## Results: list query (the 20 rows on a page)

| Scenario | Before p50 | After p50 | Before plan → after plan |
| --- | ---: | ---: | --- |
| Landing page ("best match") | 49.6 ms | **2.5 ms** | seq scan + sort all → walk `ix_repos_health`, then `ix_issues_repo_id` |
| Language = Python | 26.2 ms | **0.4 ms** | seq scan → `ix_repos_health` + `ix_issues_repo_id` |
| Easy + min 100 stars | 27.6 ms | **1.1 ms** | seq scan → `ix_repos_health` + `ix_issues_repo_id` |
| Sort = newest | 46.5 ms | **0.1 ms** | seq scan + sort → `ix_issues_open_created`, stops after 20 rows |
| Sort = recently updated | 47.9 ms | **0.1 ms** | seq scan + sort → `ix_issues_open_updated` |
| Python, updated ≤ 30 days, by stars | 21.5 ms | **0.2 ms** | seq scan → `ix_repos_stars` + `ix_issues_repo_id` |
| Page 40 (deep pagination) | 56.2 ms | **2.6 ms** | seq scan + sort → index walk |
| Text search "parser error" | 20.4 ms | 21.2 ms | unchanged: GIN `ix_issues_search_vector` was already used |

p95 values are in the raw output. They stayed within about 20% of p50 in every case.

## What the indexes did *not* fix

- **The count query** (the "N issues" total) stays at 12–28 ms. Counting 140k matching rows means visiting all of them, and no index avoids that. Possible fixes if it ever matters: cap the count (show "1,000+"), or use the planner's row estimate for unfiltered pages.
- **Text search** depends on how many rows match. The synthetic titles use a 13-word vocabulary, so "parser error" matches far more rows than it would in real text. These numbers overstate the real cost.
- **Write cost:** six more indexes means a little more work on every sync upsert. At ~1k upserts per day this is negligible.

## Why these six

Each one appeared in at least one plan above (checked with `pg_stat_user_indexes`):

| Index | Used by |
| --- | --- |
| `issues (repo_id)` | Every search joins issues to repos. Postgres does not index foreign keys automatically. |
| `issues (updated_at DESC) WHERE state = 'open'` | sort = updated. Partial: closed issues are never listed, so they stay out of the index. |
| `issues (created_at DESC) WHERE state = 'open'` | sort = newest |
| `repos (health_score DESC NULLS LAST)` | "Best match" ranking: walk the healthiest repos first, then stop once a page is full. |
| `repos (lower(language))` | The language filter, which compares `lower(language)` |
| `repos (stars DESC)` | sort = stars and the min-stars filter |
